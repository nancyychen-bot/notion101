# Notion 101 — Luma ⇄ Notion Sync

A Next.js 14 app on Vercel that links a **Notion guest database** to a **Luma event's guest list**. Organizers approve or decline applicants in Notion; those decisions push to Luma in real time. RSVPs flow from Luma into Notion automatically. The system sends transactional emails (approval with .ics invite, decline, 3-day reminder, 1-day reminder, post-event survey) and auto-declines any still-pending guests the day before each event. Only Luma events explicitly registered through the app's signup page are processed.

---

## Architecture

```
  Luma event
  RSVP / check-in ──webhook──▶  Next.js (Vercel)  ──create/update──▶  Notion guest DB
                                Neon Postgres                          (human triage)
                                (mirror + audit)   ◀──webhook──────────────┘
                                       │           approve/decline
                                       ▼
                                Resend emails
                                (approve / decline / reminders / survey)
                                Vercel Cron
                                (reminders / survey / auto-decline / retry / reconcile)
```

- **Stateless Next.js 14** (App Router, Node.js runtime, Fluid Compute) on Vercel. No long-running process; all state lives in the database.
- **Neon Postgres** — a thin mirror, dedup, and audit layer. Not the UI; not the RSVP source of truth.
- **Luma** is the RSVP source of truth. The Luma webhook drives real-time Notion updates.
- **Notion** is the human triage surface. A "Send webhook" automation on the guest database's Status property pushes approve/decline decisions back to Luma and triggers transactional email.
- **Scoping gate:** the Luma webhook handler drops events that were not registered via `/add-event`. Only Notion 101 events are ever processed.
- **Echo guard:** every outbound Notion write stamps `guests.last_synced_hash`; incoming Notion webhooks that match that hash are dropped silently, preventing feedback loops.

## Environment Variables

Copy `.env.example` to `.env.local` and fill in each value.

### Database (required)

| Variable | Description |
|----------|-------------|
| `DATABASE_URL` | Neon Postgres connection string. Injected automatically by the Vercel Neon Marketplace integration. |

### Luma (required)

| Variable | Description |
|----------|-------------|
| `LUMA_API_KEY` | Luma public API key, sent as the `x-luma-api-key` header. |
| `LUMA_WEBHOOK_SECRET` | HMAC secret for verifying incoming Luma webhook payloads (`Webhook-Signature` header). Optional in development; strongly recommended in production. |

### Notion (required)

| Variable | Description |
|----------|-------------|
| `NOTION_TOKEN` | Notion internal integration token. |
| `NOTION_GUESTS_DATA_SOURCE_ID` | Data-source ID for the guest database (Notion API v2025-09-03+). Generated by `npm run setup:notion`. |
| `NOTION_GUESTS_DB_ID` | Optional — the plain Notion database ID, used only for constructing page links in the dashboard. |
| `NOTION_WEBHOOK_SECRET` | Optional — shared secret verified in the `x-webhook-secret` header of Notion automation webhook calls. |

### Email / Resend (required)

| Variable | Description |
|----------|-------------|
| `RESEND_API_KEY` | Resend API key. |
| `COMMS_FROM` | Sender address in RFC 5322 format, e.g. `"Notion 101 <noreply@notioncommunity.com>"`. |
| `COMMS_REPLY_TO` | Optional reply-to address. |
| `COMMS_ENABLED` | Optional kill-switch. Set to `"false"` to suppress all outbound email. Defaults to `true`. |

### App (required)

| Variable | Description |
|----------|-------------|
| `APP_BASE_URL` | Public URL of the deployed app, e.g. `https://notion101.vercel.app`. Defaults to `http://localhost:3000`. |
| `CRON_SECRET` | Secret used to authenticate cron route requests (see Cron Schedule below). |
| `SURVEY_URL` | Fixed post-event survey link sent to checked-in guests. |
| `FREE_TRIAL_URL` | Notion free-trial CTA URL included in 3-day and 1-day reminder emails. Defaults to `https://www.notion.so/product`. |

### Dashboard (required)

| Variable | Description |
|----------|-------------|
| `DASHBOARD_PASSWORD` | Password for the password-protected dashboard at `/`. |
| `SESSION_SECRET` | Secret for signing the dashboard session cookie. Use a long random string. |

## Setup and Deployment Order

Follow these steps in order for a clean deployment.

**1. Create a Vercel project and add the Neon integration.**
In the Vercel dashboard, go to your project → Storage → add the **Neon** Marketplace integration. Vercel injects `DATABASE_URL` automatically into your environment.

**2. Apply the database schema.**
```bash
psql "$DATABASE_URL" -f lib/db/schema.sql
```
Alternatively, paste the contents of `lib/db/schema.sql` into the Neon SQL editor.

**3. Set all environment variables in Vercel.**
Add every variable from `.env.example` (see Environment Variables above) to your Vercel project's environment settings.

**4. Run the Notion database setup script.**
```bash
npm run setup:notion -- --parent <notion-page-id> --luma <luma-event-id-or-url>
```
This creates the guest database in Notion, reads the event's registration questions from the Luma API to derive select option lists, and writes `lib/notion/QUESTION_MAP.json` (the pinned `question_id` → Notion property mapping). Commit the generated file. Copy the resulting database IDs into `NOTION_GUESTS_DATA_SOURCE_ID` and (optionally) `NOTION_GUESTS_DB_ID` in Vercel.

**5. Configure the Notion integration and automation.**
- Share the guest database with your Notion integration (via "Connections" in the database settings).
- Add a **Status**-change "Send webhook" automation in Notion that POSTs to `/api/webhooks/notion` with the `x-webhook-secret` header set to your `NOTION_WEBHOOK_SECRET`. Optionally add "Approve" and "Decline" buttons that set Status and trigger the same webhook with an `X-Action` header.

**6. Configure the Luma webhook.**
In Luma, add a webhook for `guest.created` and `guest.updated` events (and check-in if available) pointing to `https://<your-app>/api/webhooks/luma`. Set the webhook secret to your `LUMA_WEBHOOK_SECRET`; Luma sends it as the `Webhook-Signature` header, which the app verifies via HMAC-SHA256.

**7. Register the first event.**
Navigate to `/add-event` and paste a Luma event link, or use the CLI:
```bash
npm run register:event -- --luma <luma-event-id-or-url>
```
This resolves the event, inserts it into the database, and backfills all existing Luma guests into Notion.

**8. Verify end-to-end.**
- Submit a test RSVP on Luma → the guest should appear in the Notion database.
- Change the guest's Status to "Approved" in Notion → the guest should be approved in Luma and receive the approval email with a `.ics` invite.
- Confirm reminder, survey, and auto-decline crons fire on schedule (see Cron Schedule below).

## Cron Schedule

All cron routes accept both GET and POST. They authenticate via the `x-cron-secret` request header or the `Authorization: Bearer <CRON_SECRET>` header. Vercel invokes them automatically per the schedule below.

| Route | Schedule (UTC) | Purpose |
|-------|---------------|---------|
| `/api/cron/decline-pending` | `0 13 * * *` (daily 13:00) | Auto-decline every still-pending guest for events happening tomorrow. Sends a decline email to each. |
| `/api/cron/reminders` | `0 15 * * *` (daily 15:00) | Send the 3-day and 1-day reminder emails to approved guests of upcoming events. Both windows are handled in a single pass. |
| `/api/cron/survey` | `0 * * * *` (hourly) | Send the post-event survey to checked-in guests of events that ended a few hours ago. |
| `/api/cron/comms-retry` | `*/15 * * * *` (every 15 min) | Retry `email_log` rows with status `failed`. |
| `/api/cron/reconcile` | `0 * * * *` (hourly) | Re-poll the Luma guest list for each registered upcoming event to catch any statuses or check-ins missed by the webhook. |

## Implementation Notes and Known Follow-ups

### Luma webhook payload field names are provisional

`lib/luma/parse.ts` targets an assumed webhook shape (`event.api_id`, `guest.api_id`, `registration_answers[].answer`). The OpenAPI-derived types in `lib/luma/types.ts` use a different nested shape (`data.id`, `user_email`, `registration_answers[].value`). The guest-list backfill in `lib/events/register.ts` already uses the verified type field names (from the Luma list-guests API response).

**Action required at deploy:** capture a real Luma webhook payload and compare it against `parse.ts`. Adjust the field names in `parse.ts` if they differ from the assumed shape.

### Notion webhook processing is synchronous

Next.js 14.2.15 does not export `after`/`unstable_after` without an experimental flag, so `/api/webhooks/notion` awaits all of its work — including a 3-second settle delay — before returning a 200 response to Notion. This works correctly but holds the function open for several seconds.

To restore fast-ack behavior: enable `experimental: { after: true }` in `next.config.mjs` and switch the webhook handler to use `unstable_after`, or upgrade to Next.js 15 where `after` is stable.

### Notion writes use the `data_source_id` parent

`lib/notion/push.ts` uses the data-source parent (`NOTION_GUESTS_DATA_SOURCE_ID`) per Notion API v2025-09-03+. If your installed `@notionhq/client` predates data-source support, switch the parent to `database_id` using `NOTION_GUESTS_DB_ID` instead.

### `/add-event` is intentionally not session-gated

The event signup page is designed to be embeddable in a Notion iframe (`frame-ancestors` CSP allows Notion). It is protected by a short-lived form token rather than the dashboard session. The dashboard (`/`) and the manual sync action (`/api/sync-now`) do require a valid dashboard session.

## Test Coverage

Unit tests (Vitest) cover pure logic only — no live service calls:

- Echo-guard hash: identical field set → echo; changed field → not echo.
- Luma HMAC verification (valid and tampered signatures).
- Luma webhook payload parsing (`guest.created` / `guest.updated` → normalized guest struct, including `checked_in_at`).
- Email template rendering: subject, HTML, and text are non-empty for all five email kinds; CTA and survey links are present where expected.
- Date window helpers: event falling within the 3-day or 1-day reminder window is selected; others are not.
- Notion property mappers: guest fields round-trip correctly through the Notion property format.
- `apply-status`: status mapping logic.
- `selectDeclinablePendings`: only `pending` guests are selected for auto-decline.
- Reminder audience selection: correct window logic.
- Survey audience: only guests with `checked_in_at` set are selected.

There are no integration tests against live Luma, Notion, Neon, or Resend services.
